## 一、本周做了什么：建立可复现的穷举基准实验

新增 `benchmark/runner.py`，将原来分散的 build、正确性验证和性能计数串成统一实验入口：

```bash
python -m benchmark.runner --repeat 5
```

目前注册的优化 Pass 有：

```
const_fold    常量折叠
dce           死代码消除
licm          循环不变量外提
```

runner 对它们做不重复、顺序敏感的全排列，并加入不优化的 baseline：

```
baseline：1 种
单 Pass：3 种
双 Pass 排列：6 种
三 Pass 排列：6 种
合计：16 种配置
```

本次保留原有 5 个样例，并新增 `dead_code.nl` 作为 DCE 的稳定收益案例，一共检查了 **6 × 16 = 96 组“程序—Pass 组合”**。每组都经过同一条真实工具链：

```
build(source, passes)
    → run_tests(bytecode, expected)
    → run_bench(bytecode, repeat=5)
    → 过滤错误结果
    → 按 instr_count 选择最优组合
    → 保存完整 JSON
```

选择规则与 Evaluator 保持一致：

1. **先验证正确性。** 编译失败或输出错误的候选不参与性能排名。
2. **再比较动态指令数。** `instr_count` 是确定性主指标，运行时间只作参考。
3. **指令数相同时选择更简单的组合。** 优先使用 Pass 更少、名称顺序稳定的方案。

本次实验不调用 LLM，也不评价 Agent 本身，而是穷举整个小搜索空间，得到每个程序在现有 Pass 集合下能达到的最优结果。它相当于后续实验的 **Oracle 参考线**，可以判断 LLM-only、Agent-min、Agent-full 找到的方案距离理论最优还有多远。

## 二、新增收益样例：`dead_code.nl`

此前 5 个样例中只有 `licm_demo` 能获得严格收益。为了覆盖 DCE，新增一个包含常量表达式和死代码的最小程序：

```text
let x = 2 * 3 + 4;
let dead = x * 100;
let y = x + 1;
print y;
```

变量 `dead` 的计算结果从未被使用，DCE 可以删除它及其上游临时值。优化前后都必须输出 11，但动态执行指令从 8 条下降到 6 条，形成第二个稳定、容易解释的收益案例。

把它加入 `main.py` 的默认样例顺序后，语言主链和 benchmark 都会覆盖这个程序。

## 三、实验结果

| 程序 | 覆盖能力 | baseline 指令数 | 优化后指令数 | 减少 | 收益 | 最优 Pass |
|------|---------|----------------:|---------------:|-----:|-----:|-----------|
| `basic` | 算术与表达式优先级 | 11 | 11 | 0 | 0.00% | `const_fold` |
| `branch` | if/else 与比较 | 16 | 16 | 0 | 0.00% | `const_fold` |
| `loop_sum` | while 累加 | 76 | 76 | 0 | 0.00% | `const_fold` |
| `array_dot` | 数组与多段循环 | 158 | 158 | 0 | 0.00% | `const_fold` |
| `licm_demo` | 循环不变量 | 807 | **708** | **99** | **12.27%** | `licm` |
| `dead_code` | 常量表达式与死代码 | 8 | **6** | **2** | **25.00%** | `dce` |

正确性结果：**96/96 组均编译成功、无运行错误并得到预期输出**，说明现有三个优化 Pass 的不同顺序在当前样例集上都没有改变程序语义。

两个严格收益案例：

- `licm_demo`：循环体中的 `k * n` 每轮结果相同。LICM 将它移动到循环外，动态指令数从 807 降到 708，减少 99 条。
- `dead_code`：DCE 删除未被读取的 `dead` 及相关临时计算，动态指令数从 8 降到 6，减少 2 条。

其余四个程序虽然选择出了一个正确的优化候选，但其指令数与 baseline 相同，因此只能算“无退化”，不能算性能提升。

## 四、从结果得到的结论

### 1. 现有优化器首先保证了正确性

所有 96 个候选都通过了功能测试。Pass 顺序发生变化时结果仍然正确，说明 `const_fold`、`dce`、`licm` 以及注册表的顺序调度在现有样例范围内比较稳定。

### 2. 收益取决于程序是否包含对应的优化机会

- `basic` 虽然存在常量表达式，但当前常量折叠把算术指令替换成 `copy`，没有减少动态指令数。
- `branch` 和 `loop_sum` 主要验证控制流，没有适合现有三个 Pass 的冗余计算。
- `array_dot` 虽然计算量较大，但当前保守 LICM 不移动数组访存，也没有可被 DCE 删除的死结果。
- `licm_demo` 和 `dead_code` 分别精确覆盖了 LICM、DCE 能处理的代码形状，因此可以稳定展示收益。

这说明“程序规模大”不等于“现有 Pass 一定有收益”。正式实验必须让样例覆盖优化器真正能够处理的模式，同时也应保留无收益样例，避免只展示挑选过的最好结果。

### 3. 穷举结果可以校验 LLM/Agent 是否真的有效

当前只有三个 Pass，完整组合空间很小，可以直接穷举。后续四档实验中，如果 Agent 没有为 `licm_demo` 找到包含 LICM 的 708 条方案，或者没有为 `dead_code` 找到包含 DCE 的 6 条方案，就说明它没有命中当前搜索空间中的最优结果。

最终报告除“相对 baseline 的收益”外，还可以增加：

```
Agent 最优结果 / 穷举 Oracle 最优结果
```

用于衡量 Agent 的最优命中率和搜索质量。

## 八、风险 / 待确认

- **本周结果不是四档 Agent 对比。** 它证明了优化器可以带来收益，并给出了 Oracle 上限，但还不能证明多轮 Agent 优于 LLM-only。
- **Pass 搜索空间较小。** 只有三个 Pass 时穷举成本很低，LLM/Agent 的必要性不够突出。后续可补 peephole、copy propagation 或公共子表达式消除，但应保持 IR 指令集不变。
- **运行时间噪声较大。** 部分候选虽然动态指令更少，但 Python VM 的毫秒级时间可能反向波动，因此当前仍以动态指令数作为主结论。
- **默认样例数为 6。** PDF 建议选择 3～5 个程序，正式四档实验可从中固定 5 个，或在报告中解释第 6 个是为了覆盖 DCE 的专项案例。
- **失败样例不足。** 本轮所有候选都正确，说明 Pass 较稳定，但暂时没有可用于展示“失败原因回传”的真实失败记录。
