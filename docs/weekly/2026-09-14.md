## 二、P4-1：冻结正式实验协议

正式实验不再临时选择样例或参数，而是通过配置文件固定所有影响结果的输入。这样可以避免不同配置使用不同条件，也便于之后复现实验。

### 1. 固定样例

| 程序 | 覆盖能力 | 保留原因 |
|---|---|---|
| `branch` | 条件分支 | 无收益对照样例 |
| `loop_sum` | 标量循环与累加 | 无收益对照样例 |
| `array_dot` | 数组访问与循环 | 较大动态指令数的无收益样例 |
| `licm_demo` | 循环不变量外提 | LICM 的稳定收益样例 |
| `dead_code` | 死代码消除 | DCE 的稳定收益样例 |

阶段三使用过的 `basic` 没有进入正式矩阵，最终固定为 5 个程序，以满足项目对 3～5 个样例的要求，同时保留两类明确收益和三类无收益场景。

### 2. 五档配置定义

| 配置 | LLM | 每轮候选上限 | 最大轮数 | 使用反馈 | 作用 |
|---|---:|---:|---:|---:|---|
| `baseline` | 否 | 0 | 0 | 否 | 不应用 Pass，作为性能和正确性锚点 |
| `llm_only` | 是 | 1 | 1 | 否 | 单次调用 LLM，执行一个候选，不迭代 |
| `agent_min` | 是 | 3 | 1 | 否 | 单轮生成多个候选，由执行器和评估器实测选优 |
| `agent_full` | 是 | 3 | 3 | 是 | 多轮执行，将上一轮评估反馈给下一轮 LLM |
| `oracle` | 否 | 16 | 1 | 否 | 穷举三个 Pass 的全部 16 种组合，给出理论最优参考线 |

这里的 `oracle` 不是 Agent。它通过枚举当前很小的 Pass 搜索空间得到理论最优结果，只作为比较标准。

### 3. 重复次数的含义

- `trials = 3`：完整地重复某个“程序 × 配置”实验三次，用于观察 LLM 输出、API 状态和 Agent 决策的波动。
- `bench_repeat = 5`：对一次已经生成的程序结果重复执行性能测量，时间取中位数，降低短时噪声。

因此正式矩阵的记录数为：

```text
5 个程序 × 5 个配置 × 3 个 trial = 75 条记录
```

每条记录内部又对选中结果执行 5 次 benchmark 测量。`trial` 和 `bench_repeat` 分别控制系统级重复与单次性能测量重复，不能混为同一个概念。

## 三、P4-2：补齐运行遥测与结果语义

本周不仅保存“最后选择了哪个 Pass”，还补齐了实验解释所需的过程数据。

### 1. 执行与性能指标

每个候选记录以下结果：

- 编译是否成功、运行是否报错、输出是否符合预期；
- 动态指令数 `instr_count`；
- 多次测量的运行时间及其中位数；
- Python `tracemalloc` 观测到的峰值内存；
- 候选 Pass 组合及其执行错误。

候选选择仍遵守统一规则：**先以正确性为硬门槛，再最小化动态指令数；指令数相同时优先选择 Pass 更少的方案。** 墙钟时间和 Python 内存只作为辅助信息，不参与最优候选排名。

### 2. LLM 与 Agent 指标

每次模型调用记录：

- 使用的模型和调用轮次；
- prompt、completion 和 total tokens；
- API 调用耗时；
- 模型返回的原始候选、清洗结果和淘汰原因；
- Agent 实际迭代轮数、停止原因和是否发生 baseline 回退。

### 3. `proposed_best` 与 `selected_best`

正式结果明确区分两个概念：

- `proposed_best`：只在 LLM/Agent 实际提出的候选中选最优，用于评价搜索能力；
- `selected_best`：把 baseline 也放入候选池后选出的系统最终结果，用于评价完整系统是否安全、是否退化。

这个区分很重要。例如无收益程序最终会选择空 Pass 的 baseline；这证明系统没有退化，但不能说是 LLM 主动发现了新的优化收益。

### 4. 缺失 token 的处理

如果某次 API 调用失败，服务端不会返回可靠 usage。此时配置和全局 token 总数记为缺失值，而不是错误地按 0 计算。最终报告中用 `—` 展示这种情况。

## 四、P4-3：实现统一 Matrix Runner

`benchmark/matrix.py` 中的 `run_matrix` 是正式实验的总调度器。它负责：

1. 读取并校验实验配置；
2. 按固定顺序遍历程序、配置和 trial；
3. 根据配置调用 baseline、LLM/Agent 或 Oracle 路径；
4. 对结果执行统一的正确性与性能测量；
5. 收集 Agent 轨迹、LLM usage、错误、回退与环境信息；
6. 汇总为 schema v2，并原子写入 JSON 文件。

其核心展开方式可以概括为：

```text
for sample in samples:
    for config in configs:
        for trial in range(trials):
            run_profile(sample, config, trial)
```

这样生成的每条 record 都对应唯一的 `sample + config + trial`，能够定位单次异常，也能按程序或配置做中位数汇总。

schema v2 的顶层内容包括：

```text
schema_version
generated_at
experiment
environment
configs
samples
trials
records
summary
```

实验环境中保存 Git commit 和 dirty 状态，可以判断某份结果究竟由哪一版代码生成。

## 五、P4-4：实现确定性报告生成器

新增 `benchmark/report.py`，直接从矩阵 JSON 生成 Markdown 报告。报告不重新运行实验，也不访问网络，因此只要输入 JSON 不变，输出内容就保持一致。

生成方式：

```bash
python -m benchmark.report \
  runs/final_matrix.json \
  --output docs/final_report.md \
  --strict
```

报告目前包含 15 个部分，主要覆盖：

- 项目目标、环境、配置和样例；
- 每配置正确率；
- 每程序的动态指令数、收益、时间和内存；
- Agent 提案相对 Oracle 的命中情况；
- LLM 调用次数、token、耗时和迭代轮数；
- 最优 Pass 组合及 trial 分布；
- API 错误和候选清洗原因；
- 结论、局限性与未来工作。

报告生成器还做了严格一致性检查，包括 schema 版本、记录唯一性、样例与配置完整性、baseline 存在性以及汇总数量匹配，防止用不完整 JSON 生成看似正常的报告。

### 1. 总体结果

| 指标 | 结果 |
|---|---:|
| 程序数 | 5 |
| 配置数 | 5 |

所有 75 条系统最终记录都正确，说明 baseline 锚点和正确性优先的选择策略能够阻止错误候选成为最终结果。

### 2. 每程序性能结果

下表给出各配置在 3 次 trial 上的动态指令数中位数：

| 程序 | baseline | llm_only | agent_min | agent_full | oracle | 最佳收益 |
|---|---:|---:|---:|---:|---:|---:|
| `branch` | 16 | 16 | 16 | 16 | 16 | 0.00% |
| `loop_sum` | 76 | 76 | 76 | 76 | 76 | 0.00% |
| `array_dot` | 158 | 158 | 158 | 158 | 158 | 0.00% |
| `licm_demo` | 807 | **708** | **708** | **708** | **708** | **12.27%** |
| `dead_code` | 8 | **6** | **6** | **6** | **6** | **25.00%** |

正式实验再次验证了阶段三的 Oracle 结论：

- `licm_demo` 通过 LICM 将动态指令数从 807 降至 708，减少 99 条；
- `dead_code` 通过 DCE 将动态指令数从 8 降至 6，减少 2 条；
- 其余三个程序在现有 Pass 能力下没有严格收益，系统最终选择 baseline，未发生性能退化。

### 3. LLM/Agent 配置结果

| 配置 | 正确记录 | LLM 调用 | baseline 回退 | Total tokens | 实际轮数中位数 |
|---|---:|---:|---:|---:|---:|
| `baseline` | 15/15 | 0 | 0 | 0 | 0 |
| `llm_only` | 15/15 | 15 | 9 | 13,140 | 1 |
| `agent_min` | 15/15 | 15 | 10 | — | 1 |
| `agent_full` | 15/15 | 30 | 9 | 28,668 | 2 |
| `oracle` | 15/15 | 0 | 0 | 0 | 1 |

`agent_min` 的 token 总数为 `—`，原因是其中一次 DeepSeek 超时没有返回 usage。不能将该次调用当成 0 token，所以不报告一个不完整的合计数。

### 4. Oracle 命中与 Agent 搜索质量

从系统最终选择看：

- `llm_only` 命中 Oracle：15/15；
- `agent_min` 命中 Oracle：14/15；
- `agent_full` 命中 Oracle：15/15。

`agent_min` 未命中的一次发生在 `licm_demo`：DeepSeek API 超时后系统回退到 baseline，因此该 trial 的最终指令数为 807。另两次 trial 成功选择 `licm`，所以按三次中位数汇总仍为 708。

在两个真正存在优化空间的程序上：

- `llm_only` 为 `licm_demo` 选择 `licm → const_fold → dce`，为 `dead_code` 选择 `const_fold → dce`；
- `agent_min` 成功时分别选择更短的 `licm` 和 `dce`；
- `agent_full` 三次 trial 均稳定选择 `licm` 和 `dce`，并全部在第 2 轮收敛。

### 5. 多轮 Agent 是否优于单次 LLM

本轮正式结果中，`agent_full` 相对 `llm_only`：

```text
更优程序：0
持平程序：5
更差程序：0
```

因此当前证据支持的结论是：**多轮 Agent 能稳定达到 Oracle，且候选组合通常更简洁，但没有在最终动态指令数上超过单次 LLM。**

这并不是 Agent 闭环无效，而是当前搜索空间只有三个 Pass、两个明确收益模式，单次 LLM 已经足以识别它们。不能根据本次结果声称多轮 Agent 的性能显著优于 `llm_only`。

## 八、真实异常与系统兜底

正式实验保留了异常和候选清洗事件，没有只展示成功结果。

### 1. DeepSeek API 超时

`licm_demo / agent_min / trial 1` 发生一次 `APITimeoutError`。系统记录错误并选择 baseline，保证最终输出正确，但该 trial 未获得 LICM 收益。

这次异常验证了两个设计点：

- LLM 服务不可用时，实验不会把缺失结果伪装成成功提案；
- baseline 始终参与最终选择，API 失败不会破坏程序正确性。

### 2. 重复候选清洗

`agent_min` 和 `agent_full` 中出现了重复 Pass 或重复组合，例如同一候选多次包含 `const_fold`、`dce`。系统会记录 `duplicate_pass` 或 `duplicate_combination`，再对候选去重后执行。

因此报告里的“含错误/清洗事件记录”不等于功能错误：12 条记录包含过程事件，其中只有 1 条是 API 超时，其余主要是模型候选的规范化和去重。

## 十一、本周结论

1. **项目已经具备真实的 LLM 与 Agent 路径。** `llm_only`、`agent_min` 和 `agent_full` 都实际调用 DeepSeek，不是由 Oracle 结果代替。
2. **完整系统具备安全退化能力。** LLM 返回无收益候选或 API 超时时，系统能够回到正确的 baseline，不会为追求优化而牺牲语义正确性。
3. **现有优化收益可复现。** LICM 和 DCE 两类收益在正式矩阵中与阶段三 Oracle 结果一致。
4. **多轮反馈闭环已经跑通。** `agent_full` 会执行、评估、把反馈传给下一轮并按收敛条件停止。
5. **当前实验不能证明多轮 Agent 优于单次 LLM。** 两者最终性能全部持平；更合理的解释是现有三个 Pass 构成的搜索空间太小。
6. **实验数据和结论可以追溯。** 配置、环境、原始记录、汇总、报告和测试都已经落盘。

## 十二、风险与局限

- **样例规模较小。** 当前只有 5 个正式程序，结果不能直接外推到大型程序或真实生产编译器。
- **Pass 搜索空间较小。** 只有 `const_fold`、`dce`、`licm` 三个 Pass，Oracle 仅需检查 16 种组合，尚不能充分体现 Agent 在大搜索空间中的优势。
- **收益覆盖有限。** 5 个程序中只有 2 个存在严格收益，这符合真实结果，但整体优化能力仍受当前 Pass 实现限制。
- **主指标是自定义 VM 动态指令数。** 它适合本项目内稳定比较，但不等价于原生机器码执行性能。
- **时间和内存是辅助指标。** 毫秒级墙钟时间会受 Python 和系统调度影响，`tracemalloc` 也只反映 Python 分配峰值。
- **API 具有外部波动。** 本轮已经出现一次超时；正式复现实验需要有效的 DeepSeek 配置和网络环境。
- **token 汇总存在一次缺失。** 超时调用没有 provider usage，因此 `agent_min` 和全局 token 总数不能给出完整值。
- **尚未体现 Agent 性能优势。** 如果未来需要证明多轮搜索价值，应增加 Pass 数量、相互作用更强的程序和更多 trial，而不能改写当前实验结论。

## 十三、项目最终收尾计划

阶段四核心代码和正式实验已经完成，剩余工作集中在仓库封板：

1. 对已经更新的 README 做最终复核，确认目录树、命令、配置和产物与仓库一致；
2. 复跑完整测试和快速冒烟，验证最终报告可从 JSON 无差异再生成；
3. 检查 `git diff --check`、工作区状态和正式产物是否齐全；
4. 确认仓库中不包含 API Key、临时日志或无关运行文件；
5. 提交本周报与最终验收记录；
6. 在远端认证可用后，将尚未同步的提交推送到远端仓库。

完成这些项目后，阶段四和整个项目即可正式封板。
