# 周报（截至 2026-07-12）

**方向：** 大模型智能体驱动的新语言编译与优化系统
**本周模块：** `lang/` —— 语言前端 + IR + VM（对应阶段一）

---

## 一、本周做了什么

一句话：**把 IR 从栈式字节码重构成三地址码，并给语言补上了控制流和数组——目的是让后续的优化 pass 有得可优。**

上周的第一版链路（源码 → Lark 解析树 → AST → 字节码 → VM 执行）虽然跑通了，但语言只有整数、赋值、四则运算、print，IR 是栈式的。这样的 IR 上写不了有意义的优化：没有循环就没有 LICM 的用武之地，没有数组就写不出矩阵/卷积这类计算密集负载，而栈式 IR 本身也让优化 pass 很难写。本周把这三件事一起解决了。

### 1. IR 从【栈式字节码】改成【简版三地址码 TAC】

这是本周最核心的改动，也是唯一一个"要动脑"的设计决定。

**为什么换。** 栈式 IR 的中间值**没有名字**——它们只是"栈上某个位置"。于是每写一个优化 pass，都要先在隐式的栈数据流里反推"这条 ADD 吃的是哪两个值、结果又流向了谁"：

```
PUSH 2      # 这个 2 到底喂给了哪条指令？要模拟栈才知道
PUSH 3
MUL         # 结果又流向哪里？还要继续模拟
```

三地址码给每个中间值一个显式名字（t0/t1/…），数据流直接写在指令里：

```
t0 = 2 * 3
x  = 1 + t0
```

于是三个关键 pass 都退化成"看一条指令的 dst/src"的局部判断：

| 优化 pass | 在三地址码上的判断条件 |
|-----------|----------------------|
| 常量折叠 | src 槽都是字面量 → 直接算出来，换成 copy |
| 死代码消除（DCE） | 某个 dst 之后再没被任何 src 读过 → 整条删掉 |
| 循环不变量外提（LICM） | 循环体内某条指令的 src 都是循环不变量 → 整条外提 |

**IR 服务于优化，这是换 IR 的全部理由。** 项目的价值不在"造一门强语言"，而在"能否在 IR 上自动优化并用 benchmark 证明收益"，所以 IR 的设计标准只有一条：优化好不好做。

**刻意不做的**（课设复杂度上限，避免过度设计）：不做 SSA / phi 节点、不做完整 CFG / 支配树、不做寄存器分配。控制流只用"标签 + 跳转"的线性指令序列，不建基本块图。够优化 pass 用即可。

### 2. 语言新增 if/else、while、比较运算

有循环才有优化空间。IR 层加了 `label` / `jump` / `jump_if_false`，比较运算 `< > <= >= == !=` 各生成一条三地址码指令。

### 3. 语言新增数组（按下标读写）

为的是将来能把矩阵乘法、卷积写成"嵌套循环 + 数组下标访问"——这类负载计算量大、优化收益直观。IR 层加了 `newarray` / `load_idx` / `store_idx`。

## 二、最终的 IR 指令集（阶段性定死）

指令统一是**定长 4 元组** `(op, dst, src1, src2)`，用不到的槽填 `None`。

```
copy                              变量赋值
add / sub / mul / div             标量算术
lt / gt / le / ge / eq / ne       比较（结果 1/0）
print
label / jump / jump_if_false      控制流   ← 新增
newarray / load_idx / store_idx   数组读写 ← 新增
```

三个配套的设计决定，验收时可以讲：

1. **定长 4 元组。** 每个 pass 都能无脑 `op, dst, s1, s2 = instr` 解包，不必对每种指令写不同的拆包逻辑。
2. **src 槽里 `int` 是字面量常量、`str` 是变量名。** 三地址码允许常量直接当操作数，所以常量折叠就是"看 src 槽是不是 int"。
3. **跳转类指令把 label 放在 dst 槽**（`("jump_if_false", label, cond, None)`）。这样"dst = 不被读的槽、src = 被读的槽"这条规律对**所有**指令成立，于是 `ir.uses()` / `ir.defs()` 两个辅助函数能统一实现。DCE、常量传播、LICM 将来都直接复用它们——换指令时只改这一处。

## 三、验收状态：4 个样例全部跑通

`main.py` 打印完整链路：源码 → Lark 解析树 → AST → 三地址码 IR → 执行结果 → 指令数。样例源码里用 `// expect: 55` 标注预期值，main.py 自动读出来核对，不用人肉对答案。

| 样例 | 覆盖能力 | 预期 | 状态 |
|------|---------|------|------|
| `basic.nl` | 纯算术（回归测试，确认改造没破坏原功能） | 7, 9, 16 | ✅ |
| `branch.nl` | if/else + 比较 | 17, 1 | ✅ |
| `loop_sum.nl` | while 循环（累加 1..10） | 55 | ✅ |
| `array_dot.nl` | 数组 + 循环（向量点积） | 15, 110 | ✅ |

三地址码打印成一行一条的可读形式，例如 `loop_sum.nl`：

```
    0      n = 10
    1      i = 1
    2      sum = 0
    3  L0_while:
    4      t0 = i <= n
    5      if not t0 goto L1_endwhile
    6      t1 = sum + i
    7      sum = t1
    8      t2 = i + 1
    9      i = t2
   10      goto L0_while
   11  L1_endwhile:
   12      print sum
```

**指令计数（benchmark 的核心指标）保留并扩展到了新指令。** 现在同时报告"IR 静态条数"和"实际动态执行条数"，循环程序里两者差异明显：

| 样例 | IR 静态条数 | 动态执行条数 |
|------|-----------|------------|
| basic | 11 | 11 |
| branch | 20 | 16 |
| loop_sum | 13 | **76** |
| array_dot | 46 | **158** |

`label` 是伪指令，**不计入 instr_count**——它运行时零开销（只是个地址标记）。如果计数，那么"删掉一个空标签"这种不改变任何实际工作量的变换也会显示成"收益"，会污染 benchmark 的核心指标。

## 四、基线故意保持朴素（这是设计，不是疏漏）

基线 build 不做任何优化，生成最笨的三地址码。基线越朴素，阶段三的对比表越有内容。目前已经能看到明确的下手处：

- **copy propagation**：每个赋值都多走一条 copy（`t1 = sum + i; sum = t1`）
- **公共子表达式消除（CSE）**：`array_dot.nl` 的循环体里 `i + 1` 被重复算了三次
- **LICM**：while 的条件在循环内重算，循环不变量每轮都算一遍

## 六、风险 / 待确认

- 目前语言没有函数和作用域（`let x = e;` 和 `x = e;` 在 IR 上是同一件事）。够不够阶段三用，等矩阵乘法样例写出来才能确认。
- IR 指令集应尽快**冻结**。README 里的核心原则是"锁死语言能力这个变量，才能干净地测量优化这个变量"——后面再改 IR，前面的 benchmark 数据就作废了。
