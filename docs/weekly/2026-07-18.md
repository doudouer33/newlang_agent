## 一、优化 passes（`optimizer/`）——上周计划落地 + 新增 LICM

所有 pass 都是 `f(instrs) -> instrs` 的纯函数，判断都建立在上周定的 `ir.uses()` / `ir.defs()` 上，不重新发明。

| pass | 判断（都是局部的） | 状态 |
|------|------------------|------|
| `const_fold` 常量折叠 | 两个 src 都是字面量 → 编译期算出来换成 copy | ✅ |
| `dce` 死代码消除 | 某个 dst 之后再没被读 → 整条删（含回跳陷阱的处理） | ✅ |
| `licm` 循环不变量外提 | 循环体里每轮算同一值的指令 → 提到循环外只算一次 | ✅ **本周新增** |
| `registry` pass 注册表 | 名字 → 函数，按顺序串成流水线 | ✅ |

**LICM 是本周唯一"要动脑"的 pass。** 难点在于 README 刻意不建 CFG / 支配树，得在纯线性指令序列上安全地识别循环、判断不变量。做法：

- **靠"回跳"找循环**：IRBuilder 生成的 while 是固定套路，一条目标标签在自己之前的跳转（backward jump）就唯一标识出一个循环区间。if 只向前跳，不会误判成循环。
- **只提"纯标量临时变量"且排除 div**：只外提 `copy / add / sub / mul / 比较` 且 dst 是编译器临时变量 `t0/t1/…` 的指令。临时变量在全程单赋值、定义即使用同块，这个性质保证外提不会覆盖别处的值、也不会有"某轮没执行到 def 却读到它"的路径。**div 单独排除**：循环若一轮没进，把 div 提到外面会凭空触发本不该发生的除零。
- **不动点迭代**：提出一个临时变量后，只依赖它的下一条也随之够格；嵌套循环则一层层往外提。

配了一个试金石样例 `licm_demo.nl`（循环体里 `k * n` 是纯不变量），收益能被指令数干净量出来：**baseline 807 → licm 708**，每轮少算一次乘法，结果仍是 30000。

> **pass 顺序本身是变量**：先 const_fold 再 dce，和只跑 dce，收益完全不同。registry 把"跑哪些、按什么顺序"变成一个字符串列表，正是为了让上层的 Agent 去搜索这个组合空间。

## 二、工具链（`tools/`）——Agent 唯一能"动手"的地方

四个工具 + 一个 Tool Router，统一 `dict 进 / dict 出`：

```
build(source, passes)        -> {ok, bytecode, error}      源码 → 优化后 IR
run_tests(bytecode, expected)-> {correct, output, error}   执行 + 对答案
run_bench(bytecode, repeat)  -> {instr_count, time_ms, error}  计时 + 数指令
save_result(data, name)      -> {ok, path, error}          落盘 runs/<时间戳>.json
call_tool(name, inp)         Tool Router：按名字分发，名字没注册就抛 UnknownToolError
```

三条纪律贯穿始终：

1. **统一 dict 进 dict 出**——两头都能直接 `json.dump` 进 runs/，一次调用即一条可复现记录。
2. **内部不许崩**——编译错、运行错（死循环、越界、除零）全 catch 住、如实填进 `error` 字段，不让异常冒泡。
3. **只报事实、不做判断**——编译成没成、结果对不对、跑了多少指令；好坏排序留给 Evaluator。

两个关键设计点（验收可讲）：

- **`apply_passes` 是唯一做优化的地方，`build` 自身零优化逻辑。** `passes=[]` 就是 baseline，baseline 和优化档共用同一条路径，唯一差别是 passes 列表——不给 baseline 开小灶，两边才干净可比。
- **run_bench 两个指标地位不同**：`instr_count` 是确定性的（同段 IR 恒定、label 不计），是收益**主对比信号**，也是唯一能写进断言的；`time_ms` 会抖（GC/调度），仅作参考，用来发现"指令数降了但时间反涨"这类异常，不拿来排名。

## 四、阶段二：LLM + 多智能体优化闭环（本周主体）

### 1. 数据契约 `Candidate`（`contracts.py`）

**Agent 之间不传自然语言，只传结构化对象。** 一个 Candidate 就是「某样例 + 某套 pass 组合」这一个候选，从生成 → 编译 → 测试 → 评估一路被逐字段回填。放在顶层（不属于任何子包），谁都能 import 且不产生循环依赖。带 `to_dict/from_dict`（日志即 JSON）、`is_viable()`（编译成功且正确才可比）。

### 2. LLM 封装 `llm/`（DeepSeek）

- **供应商 DeepSeek，走 OpenAI 兼容 SDK**（`base_url=https://api.deepseek.com`，模型 `deepseek-v4-flash`），`response_format=json_object` 强制结构化输出。
- 核心方法 `complete_json(user, system, schema) -> dict`：上层只依赖这一个口子，换供应商只改这个包。
- `DeepSeekClient` 底层客户端**懒构造**（没密钥也能建对象、导入测试都不被卡），错误统一收口成 `LLMError`；`StubLLMClient` 离线桩供测试。密钥经 `.env` 注入，绝不硬编码。

### 3. 四个 Agent + 编排循环（`agents/`）

每个 Agent 只做一件事，靠共享 `context` 字典逐步传递、逐步填充：

| Agent | 职责 |
|-------|------|
| **Planner** | 最小固定流程（不调 LLM）：锁定可用 pass 集合 + 候选数 |
| **OptimizerAgent** | 把 baseline IR 喂给 LLM 判断，产出候选后**清洗**（只留注册过的 pass、顺序去重、丢空组合、截断 n）才包成 origin='llm' 的未执行 Candidate |
| **Executor** | **唯一碰工具链**，经 Tool Router 依次 build→run_tests→run_bench，原地回填 Candidate；只报事实、不排序 |
| **Evaluator** | **唯一判断好坏**：过正确性 → 按 instr_count 排序（不按会抖的 time_ms）→ 选最优 → 打包反馈 |

**orchestrator（系统的心脏）** 把它们串成多轮闭环，三个编排决定都落实了 README 的意图：

- **每轮注入 baseline 锚点**：排名和反馈始终有"不优化会怎样"作参照，最优也有保底；
- **Evaluator 的 feedback 喂回下一轮 OptimizerAgent**：形成"生成→执行→评估→再生成"的闭环；
- **收敛即停 + 落盘 runs/**：某轮没刷新历史最优就停，整轮历史写成一个 JSON 存下来可复现。

一条纪律贯穿：**LLM 负责"想"（生成候选草案），Agent 负责"管"（清洗、编排、判定），工具链负责"真跑"。** LLM 的输出一律当不可信草案，落到可执行之前先过校验。

## 五、验收：真调 DeepSeek，全系统端到端跑通

`orchestrate('licm_demo', source)` 一行驱动完整闭环。DeepSeek 看着真实 IR 正确识别出这段循环里的不变量、给出含 licm 的候选：

| 候选 | correct | instr_count | 相对基线省 |
|------|---------|-------------|-----------|
| baseline（`[]`） | ✓ | 807 | — |
| `[licm]` | ✓ | **708** | 99 |
| `[licm, dce]` | ✓ | 708 | 99 |
| `[const_fold, licm]` | ✓ | 708 | 99 |

多轮行为：**round 0 进步到 708 → round 1 无更优 → 自动收敛停止**（2 轮），最优 `[licm]`（并列时因 pass 更少压过 `[licm, dce]`），结果落盘 `runs/*.json`。

> 这不只达成了阶段二"生成候选→运行测试→输出结果最小闭环"的成功标准，还**超出**：实际做到了多轮迭代 + 反馈回传 + 自动收敛 + 落盘。

## 七、风险 / 待确认

- **pass 组合空间还小**：目前只有 const_fold / dce / licm 三个（peephole 未实现），LLM 能搜的组合有限。样例里目前只有 `licm_demo` 真含循环不变量，别的样例 LICM 无收益属正常——阶段三补矩阵样例后 LICM 的用武之地会更明显。
- **模型输出的稳健性**：`deepseek-v4-flash` 偶发不稳，已用 JSON 模式强约束 + OptimizerAgent 侧清洗兜底（未知 pass 剔除、去重、容错），LLM 失败会收口成空候选而非崩溃。
- **密钥安全**：DeepSeek key 存在 `.env`（已 gitignore），务必不要入库。
- **IR 已冻结**，符合"锁死语言能力这个变量，才能干净地测量优化"的原则；阶段三不应再动 IR，否则前面的 benchmark 数据作废。
